PART 2: DYNAMIC CLASS INJECTION - _apply_to_module() EXPLAINED
================================================================================

QUESTION ADDRESSED:
"Please explain this code: _apply_to_module()"

LOCATION: torch/distributed/fsdp/_fully_shard/_fsdp_init.py, lines 404-427

FUNCTION SIGNATURE:
--------------------
def _apply_to_module(
    modules: list[nn.Module],
    cls_to_fsdp_cls: dict[type, type],
    fsdp_module_class: type,
    class_name_suffix: str,
    deepcopy_fn: Callable[[Any], Any],
):

PURPOSE:
--------
Dynamically creates and injects wrapper classes that inherit from both the 
FSDP functionality class and the original module class. This makes FSDP 
available to arbitrary user modules without requiring explicit inheritance.

MECHANISM:
----------
1. DYNAMIC CLASS CREATION:
   For each unique original class in the module hierarchy, creates a new class
   with dual inheritance:
   
   class FSDP<OriginalClassName>(FSDPModule, OriginalModule):
       pass

2. MRO (Method Resolution Order):
   [FSDP<Orig>, FSDPModule, Orig, ...]
   
   This ensures:
   - FSDP methods have highest priority (checked first)
   - FSDPModule provides FSDP functionality
   - Original class is next in MRO for fallback
   - Index 2 points to original class

3. CLASS CACHING:
   New classes are cached in cls_to_fsdp_cls dictionary to avoid
   recreating the same class multiple times

4. MODULE REBINDING:
   Each module instance is rebound to the new dynamically created class
   while preserving its internal state.

EXAMPLE FLOW:
-------------
Input Module:
  class MyModel(nn.Module):
      def __init__(self):
          self.layer = nn.Linear(10, 10)

After fully_shard(model):
  
  Dynamically created class:
    class FSDPMyModel(FSDPModule, MyModel):
        pass
  
  model instance now has type: FSDPMyModel
  model can now call: reshard(), unshard(), set_requires_gradient_sync(), etc.


KEY INSIGHT:
-----------
This design is crucial because:
- User modules don't need to inherit from FSDPModule
- Multiple different module types can be FSDP-wrapped independently
- Each wrapped module gets full FSDP functionality without code modification
- Clean separation: FSDP logic is orthogonal to module logic

HIGH-LEVEL FLOW:
----------------

Module Forward Flow:
  1. Pre-forward hook triggered (registered in _pre_forward)
  2. All-gather parameters across distributed workers
  3. Wait for all-gather to complete
  4. Execute module's forward computation
  5. Post-forward hook triggered
  6. Optionally reshard (squeeze back to sharded form)

STEP 3: COLLECTIVE ALL-GATHER OPERATION (lines 325-397)
=========================================================

Function: foreach_all_gather() in _fsdp_collectives.py

Two-stage all-gather process:

Stage 1: Copy-in (Prepare data for communication)
  - Input: Sharded parameters on device
  - Operation: torch.ops.fsdp.all_gather_copy_in()
  - Output: all_gather_input buffer
  - Buffer size: all_gather_input_numel (not multiplied)

Stage 2: Collective Communication
  - Input: all_gather_input buffer
  - Operation: all_gather_comm()
    - Allocates output buffer: size = input_numel * world_size
    - Performs collective all-gather
    - All workers gather all parameters
  - Output: all_gather_output buffer (size = input_numel * world_size)

Stage 3: Copy-out (Finalize parameters)
  - Input: all_gather_output buffer
  - Operation: Register output in param.unsharded_data
  - Result: Parameters now unsharded and registered

Memory Layout (All-gather):
  Before:
    Worker 0: [P0 chunk]
    Worker 1: [P1 chunk]
    Worker 2: [P2 chunk]
    Worker 3: [P3 chunk]
  
  After all-gather:
    Worker 0: [P0 chunk, P1 chunk, P2 chunk, P3 chunk]
    Worker 1: [P0 chunk, P1 chunk, P2 chunk, P3 chunk]
    Worker 2: [P0 chunk, P1 chunk, P2 chunk, P3 chunk]
    Worker 3: [P0 chunk, P1 chunk, P2 chunk, P3 chunk]


STEP 4: FORWARD COMPUTATION
=========================================================

The module's forward() method now executes with full unsharded parameters.
Computation can happen on all gathered parameters without resharding in between.


STEP 5: POST-FORWARD RESHARDING (_fsdp_state.py, lines 301-323)
=========================================================

Method: _post_forward(module, args, output)

Decision point: Check reshard_after_forward flag

If reshard_after_forward == True:
  - Call reshard() to squeeze parameters back to sharded form
  - Free unsharded parameters
  - Register sharded parameters to module
  - Save memory for backward pass
  
  Pseudocode:
    for param_group in param_groups:
        param_group.reshard()
        # Resharding process:
        #   1. Reshape unsharded parameter to original shape
        #   2. Shard along dim-0
        #   3. Create DTensor with Shard(0) placement
        #   4. Register as module parameter

If reshard_after_forward == False:
  - Keep unsharded parameters in memory
  - Avoid all-gather in backward
  - Trade higher memory for reduced communication
  - Default for root module


STREAM MANAGEMENT:
------------------
- all_gather_copy_in_stream: Overlaps copy-in with computation
- all_gather_stream: Waits before forward computation starts
- Synchronization: all_gather_stream.wait_stream(all_gather_copy_in_stream)


KEY DESIGN DECISIONS:
---------------------
1. Two-stage all-gather (copy-in + collective) allows overlap
2. Reshard is optional - trades memory vs communication
3. State-level (module) vs param-group-level separation
   - State handles orchestration
   - Param groups handle execution
4. Hook-based integration with nn.Module
   - Pre-forward and post-forward hooks manage FSDP ops

STEP 4: POST-BACKWARD REDUCTION (lines 516-600+)
=========================================================

Method: post_backward() in FSDPParamGroup

Complex process with multiple stages:

Stage 1: Gradient Accumulation
  - Gradients computed by autograd
  - Accumulated in param.grad

Stage 2: Reshape/Rechunk for Reduction
  - Input: Unsharded gradients (shape = original shape)
  - Operation: Reshape to match forward all-gather layout
  - Purpose: Prepare for reduce-scatter operation
  
  Example:
    Original param shape: (100, 100)
    world_size: 4
    
    After reshape for reduce-scatter:
      Shape: (25, 100) on each worker (100 / 4 = 25)
      But conceptually in reduce-scatter layout:
        Worker 0: gradient chunk [0:25, :]
        Worker 1: gradient chunk [25:50, :]
        Worker 2: gradient chunk [50:75, :]
        Worker 3: gradient chunk [75:100, :]

Stage 3: Reduce-scatter Collective
  Function: foreach_reduce() in _fsdp_collectives.py (lines 524-678)
  
  Process:
    1. Allocate reduce_scatter_input buffer
       Size: total_gradient_numel
    2. Copy-in gradients to input buffer
       Operation: torch.ops.fsdp.reduce_scatter_copy_in()
    3. Perform reduce-scatter collective
       - All workers send their full gradient
       - Result: Each worker gets reduced gradient for its shard
       - Collective operation:
         reduce_scatter_comm(
             reduce_scatter_input,
             reduce_scatter_output,
             group=reduce_scatter_group,
         )
    4. Output buffer allocation
       Size: total_gradient_numel / world_size
       
  Example output:
    Worker 0 receives: reduced gradient [0:25, :]
    Worker 1 receives: reduced gradient [25:50, :]
    Worker 2 receives: reduced gradient [50:75, :]
    Worker 3 receives: reduced gradient [75:100, :]


Memory Layout (Reduce-scatter):
  Before:
    Worker 0: full_grad [0:100, :]
    Worker 1: full_grad [0:100, :]
    Worker 2: full_grad [0:100, :]
    Worker 3: full_grad [0:100, :]
  
  After reduce-scatter:
    Worker 0: reduced_grad [0:25, :]     (sum of all workers' [0:25, :])
    Worker 1: reduced_grad [25:50, :]   (sum of all workers' [25:50, :])
    Worker 2: reduced_grad [50:75, :]   (sum of all workers' [50:75, :])
    Worker 3: reduced_grad [75:100, :]  (sum of all workers' [75:100, :])


Stage 4: Reshard for Optimizer
  - After reduce-scatter: gradients are sharded by dim-0
  - Create DTensor with Shard(0) placement
  - Result: Gradients match parameter sharding for optimizer step


Stage 5: Free Unsharded Parameters
  - Unsharded parameters from backward are freed
  - Only sharded parameters remain for optimizer
  
  Pseudo-code:
    for param in fsdp_params:
        param.unsharded_data = None
        param.data = param.sharded_param  # DTensor with Shard(0)


ARCHITECTURAL LAYERS:
---------------------
1. Module Level (_fsdp_state.py)
   - _pre_backward(): Coordinates backward across param groups
   - _root_post_backward_final_callback(): Finalizes backward
   
2. Param Group Level (_fsdp_param_group.py)
   - pre_backward(): Prepares group for backward
   - post_backward(): Manages gradient reduction
   
3. Collective Level (_fsdp_collectives.py)
   - foreach_reduce(): Executes reduce-scatter communication
   - Handles device placement, dtype, stream management


STREAM MANAGEMENT:
------------------
- all_gather_copy_in_stream: Used in pre_backward for all-gather
- all_gather_stream: Used in pre_backward for all-gather
- reduce_scatter_stream: Used in post_backward for reduce-scatter
- Synchronization ensures dependencies between stages


KEY DESIGN INSIGHTS:
--------------------
1. Pre-backward all-gathers only if resharded after forward
   - Saves communication if reshard_after_forward=False
2. Reduce-scatter reduces all gradients efficiently
   - Each worker keeps only its shard
3. State machine tracks backward progression
   - Prevents incorrect hook firing
4. Gradient division factor support
   - Allows custom reduce operations (e.g., NCCL PreMulSum)

   - Allows independent prefetching strategies

OVERVIEW:
=========

FSDP uses two main collective communication operations:

1. ALL-GATHER
   - When: Pre-forward (and pre-backward if resharded)
   - What: Gather all parameter shards from all workers
   - Why: Need full parameters for forward computation
   - Result: Each worker has complete unsharded parameters

2. REDUCE-SCATTER
   - When: Post-backward
   - What: Reduce gradients and scatter results
   - Why: Each worker keeps only its gradient shard
   - Result: Each worker has reduced gradient for its shard

-----------------------

Two independent streams manage overlap:

  all_gather_copy_in_stream (stream 1):

    - Can overlap with forward computation

    - Runs collective communication

    - Computation waits on this stream before forward

SUMMARY: ARCHITECTURAL PATTERNS IN FSDP2
================================================================================

KEY DESIGN PATTERNS:
====================

1. TWO-LAYER ARCHITECTURE (State vs ParamGroup)
   - State level: Orchestration, coordination, global decisions
   - ParamGroup level: Execution, fine-grained control
   - Enables flexibility and modularity

2. HOOK-BASED INTEGRATION
   - Pre-forward hooks for all-gather
   - Post-forward hooks for optional reshard
   - Pre-backward hooks for all-gather (if needed)
   - Post-backward hooks for reduce-scatter
   - Clean integration with nn.Module

3. TWO-STREAM DESIGN FOR OVERLAP
   - Copy-in stream (compute-like operations)
   - Communication stream (collective operations)
   - Enables overlap of CPU operations and collective

4. DYNAMIC CLASS INJECTION
   - Wraps arbitrary modules without inheritance
   - Preserves module semantics
   - Clean separation of concerns

5. MULTI-STAGE COLLECTIVES
   - Copy-in: Prepare data for communication
   - Collective: Actual distributed operation
   - Copy-out: Finalize for computation
   - Allows customization at each stage

6. OPTIONAL RESHAPE AFTER FORWARD
   - reshard_after_forward=True: Save memory
   - reshard_after_forward=False: Save communication
   - reshard_after_forward=int: Hybrid approach
   - Flexible memory/communication tradeoff


EXECUTION FLOW SUMMARY:
=======================

FORWARD PASS:
  1. Module forward called
  2. Pre-forward hook: all-gather parameters
  3. Forward computation with unsharded parameters
  4. Post-forward hook: optionally reshard (free unsharded)
  5. Forward complete

BACKWARD PASS:
  1. Autograd backward starts
  2. Pre-backward hook: re-all-gather if resharded
  3. Autograd computes gradients
  4. Post-backward hook: reduce-scatter gradients
  5. Optimizer step on sharded gradients
  6. Backward complete

MEMORY USAGE:
  Peak forward: param_size * world_size (if not resharding)
  Peak backward: param_size * world_size (during all-gather)
  Minimum: param_size (only sharded parameters)


COMMUNICATION VOLUME:
=====================

Per iteration:
  Forward: world_size * param_size bytes (all-gather)
  Backward: world_size * param_size bytes (reduce-scatter)
  Total: 2 * world_size * param_size bytes per iteration

Optimizations:
  - Reshard after forward reduces backward all-gather
  - Prefetching overlaps communication with computation
  - Mixed precision reduces communication size


STATE MACHINE:
==============

States:
  IDLE -> FORWARD -> (POST_FORWARD) -> 
  PRE_BACKWARD -> POST_BACKWARD -> IDLE

Hooks:
  Pre-forward: IDLE -> FORWARD
  Pre-backward: Forward -> PRE_BACKWARD
  Post-backward: PRE_BACKWARD -> POST_BACKWARD (or IDLE)
