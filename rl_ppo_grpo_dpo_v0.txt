SECTION 2 — PPO vs GRPO STRUCTURAL COMPARISON
================================================================

Reference files:
  PPO: https://github.com/huggingface/trl/blob/fc4dae256d924dfbb906af9c2e817bc6fb7b590b
       trl/trainer/ppo_trainer.py  lines 513-577
  GRPO: https://github.com/huggingface/trl/blob/main/trl/trainer/grpo_trainer.py

The PPO code around line 517 has TWO closely related sections:

  A) Advantage computation via GAE (lines 513-525)
  B) Training loop with clipped policy loss (lines 528-577)

GRPO has parallel sections in different methods:

  A) Advantage computation via group-relative normalization
     -> _generate_and_score_completions()  lines 2142-2167
  B) Clipped policy loss
     -> _compute_loss()                    lines 2436-2587

The key structural difference is:

  PPO needs TWO networks:  policy model + value model (critic)
  GRPO needs ONE network:  policy model only

This changes everything downstream:
  - How advantages are computed
  - Whether advantages are per-token or per-sequence
  - Whether a value loss term exists
  - How KL is enforced

SECTION 3 — PPO ADVANTAGE COMPUTATION (GAE)
================================================================

Source: ppo_trainer.py lines 513-525

CODE:
------
    # 4. compute rewards
    kl = logprobs - ref_logprobs                      # shape: (batch, T)
    non_score_reward = -args.kl_coef * kl             # per-token KL penalty
    rewards = non_score_reward.clone()

    # Scalar reward model score added at LAST REAL TOKEN only
    actual_end = torch.where(sequence_lengths_p1 < rewards.size(1),
                             sequence_lengths_p1, sequence_lengths)
    rewards[[actual_start, actual_end]] += scores     # scores shape: (batch,)

    # 6. compute advantages and returns
    lastgaelam = 0
    advantages_reversed = []
    gen_length = responses.shape[1]
    for t in reversed(range(gen_length)):             # LINE 517
        nextvalues = values[:, t + 1] if t < gen_length - 1 else 0.0
        delta = rewards[:, t] + args.gamma * nextvalues - values[:, t]
        lastgaelam = delta + args.gamma * args.lam * lastgaelam
        advantages_reversed.append(lastgaelam)
    advantages = torch.stack(advantages_reversed[::-1], axis=1)
    returns = advantages + values
    advantages = masked_whiten(advantages, ~padding_mask)
    advantages = torch.masked_fill(advantages, padding_mask, 0)


FORMULA (GAE):
--------------
    delta_t   = r_t + gamma * V(s_{t+1}) - V(s_t)        (TD error at step t)
    A_t^GAE   = delta_t + gamma * lam * delta_{t+1}
                         + (gamma*lam)^2 * delta_{t+2} + ...

Where:
    r_t       = reward at token t  (KL penalty + reward_model_score at last token)
    V(s_t)    = value network prediction at position t
    gamma     = discount factor
    lam       = GAE lambda (controls bias-variance tradeoff)

EXAMPLE:
--------
Sequence A, gen_length=4, gamma=1.0, lam=0.95:

    rewards  = [-0.02, -0.01, -0.03, -0.01 + 2.5]  (last token gets reward score)
             = [-0.02, -0.01, -0.03,  2.49]

    values   = [0.8,   0.6,   0.4,   0.1]           (critic predictions)

Backward pass:
    t=3: delta = 2.49 + 0 - 0.1 = 2.39
         lastgaelam = 2.39

    t=2: delta = -0.03 + 1.0*0.1 - 0.4 = -0.33
         lastgaelam = -0.33 + 1.0*0.95*2.39 = -0.33 + 2.27 = 1.94

    t=1: delta = -0.01 + 1.0*0.4 - 0.6 = -0.21
         lastgaelam = -0.21 + 1.0*0.95*1.94 = -0.21 + 1.843 = 1.633

    t=0: delta = -0.02 + 1.0*0.6 - 0.8 = -0.22
         lastgaelam = -0.22 + 1.0*0.95*1.633 = -0.22 + 1.551 = 1.331

    advantages_reversed = [2.39, 1.94, 1.633, 1.331]
    advantages (forward) = [1.331, 1.633, 1.94, 2.39]   shape: (batch, T)

KEY POINT: Every token position has a DIFFERENT advantage value.
Token t=3 advantage = 2.39  (very good — this is where the reward landed)
Token t=0 advantage = 1.331 (good, but discounted because it is earlier in sequence)

SECTION 4 — GRPO ADVANTAGE COMPUTATION
================================================================

Source: grpo_trainer.py lines 2142-2167 (_generate_and_score_completions)

CODE:
------
    # rewards shape: (B,)  — one scalar per completion from reward function(s)
    rewards = (rewards_per_func * self.reward_weights).nansum(dim=1)

    # Group-relative: compare each completion to siblings from SAME prompt
    mean_grouped_rewards = rewards.view(-1, num_generations).mean(dim=1)
    mean_grouped_rewards = mean_grouped_rewards.repeat_interleave(num_generations, dim=0)

    std_rewards = rewards.view(-1, num_generations).std(dim=1)
    std_rewards = std_rewards.repeat_interleave(num_generations, dim=0)

    advantages = rewards - mean_grouped_rewards          # center within group
    advantages = advantages / (std_rewards + 1e-4)       # normalize within group
    # advantages shape: (B,)  — ONE scalar per completion, not per token


FORMULA:
--------
    A_i = (R_i - mean(R_1, R_2, ..., R_G)) / std(R_1, R_2, ..., R_G)

Where:
    R_i = reward for completion i
    G   = num_generations (number of completions per prompt, e.g. 8)

EXAMPLE:
--------
Prompt: "Solve: 2+2"
G = 4 completions generated:
    C1: "4"           reward = 1.0  (correct)
    C2: "The answer is 4"  reward = 0.8  (correct but verbose)
    C3: "I think 5"   reward = -1.0 (wrong)
    C4: "4.0"         reward = 0.9  (correct)

    mean = (1.0 + 0.8 + (-1.0) + 0.9) / 4 = 1.7/4 = 0.425
    std  = std([1.0, 0.8, -1.0, 0.9]) ≈ 0.83

    advantages:
    C1: (1.0  - 0.425) / 0.83 = +0.69
    C2: (0.8  - 0.425) / 0.83 = +0.45
    C3: (-1.0 - 0.425) / 0.83 = -1.72
    C4: (0.9  - 0.425) / 0.83 = +0.57

KEY POINT: One scalar per completion. All tokens in C1 share advantage +0.69.
C3 was the worst in the group → large negative advantage → its tokens are penalized.

SECTION 5 — PPO TRAINING LOOP (CLIPPED POLICY LOSS)
================================================================

Source: ppo_trainer.py lines 528-577

CODE:
------
    # Multiple PPO epochs with fresh random shuffle each epoch
    for ppo_epoch_idx in range(args.num_ppo_epochs):
        b_inds = np.random.permutation(args.local_batch_size)
        for mini_batch_start in range(0, args.local_batch_size, args.local_mini_batch_size):
            mini_batch_end   = mini_batch_start + args.local_mini_batch_size
            mini_batch_inds  = b_inds[mini_batch_start:mini_batch_end]
            for micro_batch_start in range(0, args.local_mini_batch_size,
                                           args.per_device_train_batch_size):
                with accelerator.accumulate(model):
                    micro_batch_end  = micro_batch_start + args.per_device_train_batch_size
                    micro_batch_inds = mini_batch_inds[micro_batch_start:micro_batch_end]

                    mb_advantage = advantages[micro_batch_inds]     # (mb, T)
                    mb_responses = responses[micro_batch_inds]
                    mb_logprobs  = logprobs[micro_batch_inds]
                    mb_return    = returns[micro_batch_inds]
                    mb_values    = values[micro_batch_inds]

                    # Forward pass
                    output, vpred_temp = forward(model, mb_query_responses, pad_token_id)
                    logits = output.logits[:, context_length - 1 : -1]
                    logits /= args.temperature + 1e-7
                    new_logprobs = selective_log_softmax(logits, mb_responses)

                    # Value function loss (clipped)
                    vpred = vpred_temp[:, context_length - 1 : -1].squeeze(-1)
                    vpredclipped = torch.clamp(vpred,
                                              mb_values - args.cliprange_value,
                                              mb_values + args.cliprange_value)
                    vf_losses1   = torch.square(vpred - mb_return)
                    vf_losses2   = torch.square(vpredclipped - mb_return)
                    vf_loss      = 0.5 * masked_mean(torch.max(vf_losses1, vf_losses2), ...)

                    # Policy gradient loss (clipped PPO-clip)
                    logprobs_diff = new_logprobs - mb_logprobs      # log(pi_new / pi_old)
                    ratio         = torch.exp(logprobs_diff)        # r_t = pi_new / pi_old
                    pg_losses     = -mb_advantage * ratio
                    pg_losses2    = -mb_advantage * torch.clamp(ratio, 1.0 - args.cliprange,
                                                                        1.0 + args.cliprange)
                    pg_loss_max   = torch.max(pg_losses, pg_losses2)
                    pg_loss       = masked_mean(pg_loss_max, ~padding_mask[micro_batch_inds])

                    loss = pg_loss + args.vf_coef * vf_loss
                    accelerator.backward(loss)
                    optimizer.step()
                    optimizer.zero_grad()


FORMULA (PPO-clip):
-------------------
    r_t(theta) = pi_theta(a_t | s_t) / pi_old(a_t | s_t)     (importance ratio)

    L_CLIP = E_t[ min(r_t * A_t,  clip(r_t, 1-eps, 1+eps) * A_t) ]

    Total loss = -L_CLIP + vf_coef * L_VF

Where L_VF = value function loss (clipped MSE between predicted and actual returns).

LOOP STRUCTURE:
---------------
    Outer loop:   num_ppo_epochs   (reuse same rollout data, e.g. 4 times)
    Middle loop:  mini-batches     (random shuffle to break correlation)
    Inner loop:   micro-batches    (gradient accumulation across devices)

SECTION 6 — GRPO CLIPPED POLICY LOSS
================================================================

Source: grpo_trainer.py lines 2436-2587 (_compute_loss)

CODE:
------
    # Per-token log probs from current model
    per_token_logps, entropies = self._get_per_token_logps_and_entropies(model, ...)

    # Sequence-level advantage (one scalar per completion)
    advantages = inputs["advantages"]           # shape: (B,)
    if advantages.dim() == 1:
        advantages = advantages.unsqueeze(1)    # shape: (B, 1)  for broadcasting

    # Reference log probs (precomputed or from frozen ref model)
    old_per_token_logps = inputs.get("old_per_token_logps")
    old_per_token_logps = per_token_logps.detach() if old_per_token_logps is None \
                          else old_per_token_logps

    # Importance sampling ratio (token or sequence level — see Section 9)
    log_ratio  = per_token_logps - old_per_token_logps   # shape: (B, T)
    coef_1     = torch.exp(log_importance_weights)       # shape: (B,T) or (B,1)
    coef_2     = torch.clamp(coef_1, 1 - self.epsilon_low, 1 + self.epsilon_high)

    # Clipped policy loss (GRPO default: loss_type == "grpo")
    per_token_loss1 = coef_1 * advantages       # (B,T) * (B,1) broadcasts to (B,T)
    per_token_loss2 = coef_2 * advantages
    per_token_loss  = -torch.min(per_token_loss1, per_token_loss2)

    # KL divergence term (if beta != 0)
    if self.beta != 0.0:
        per_token_kl = torch.exp(ref_per_token_logps - per_token_logps) \
                       - (ref_per_token_logps - per_token_logps) - 1
        per_token_loss = per_token_loss + self.beta * per_token_kl

    # Aggregate: mean over tokens, then mean over batch
    loss = ((per_token_loss * mask).sum(-1) / mask.sum(-1).clamp(min=1.0)).mean()


FORMULA (GRPO):
---------------
    r_t(theta) = exp(log pi_theta(a_t) - log pi_old(a_t))   (per-token ratio)

    L_GRPO = -E[ min(r_t * A_seq,  clip(r_t, 1-eps_lo, 1+eps_hi) * A_seq) ]
             + beta * KL(pi_ref || pi_theta)

Where A_seq is the SAME for all tokens in the sequence (see Section 4).

LOOP STRUCTURE:
---------------
    No explicit epoch loop in the code — HuggingFace Trainer handles it.
    num_iterations controls how many times same rollout data is reused.
    No manual mini-batch shuffling — Trainer manages gradient accumulation.

SECTION 7 — PPO LOSS: TRULY PER-TOKEN
================================================================

In PPO, EVERY token position has a DISTINCT advantage value because:

1. KL penalty is applied at every token:
       non_score_reward = -kl_coef * (logprobs - ref_logprobs)   shape: (batch, T)

2. Reward model score is added only at the LAST real token:
       rewards[[actual_start, actual_end]] += scores

   So the reward array looks like:
       Token:   t=0     t=1     t=2     t=3(last)   t=4(pad)
       Seq A: [-0.02,  -0.01,  -0.03,  -0.01+2.5,   0      ]
               KL       KL       KL      KL + score

3. Value network predicts future return at every position:
       values shape: (batch, T) — one prediction per token

4. GAE combines all of the above into per-token advantages:
       advantages shape: (batch, T) — different at every position

CONCRETE EXAMPLE (per-token credit assignment):
-----------------------------------------------
    Seq A: ["The", "cat", "sat"] advantage = [1.33, 1.63, 1.94]
            token 0              token 1     token 2

    Meaning:
    - "sat" (t=2) advantage=1.94: very good token choice, close to the reward
    - "The"  (t=0) advantage=1.33: also good but more discounted (earlier in sequence)

PPO can say: "token 'sat' was a better choice than 'The'" — fine-grained credit.

SECTION 8 — GRPO LOSS: SEQUENCE-LEVEL ADVANTAGE BROADCAST TO ALL TOKENS
================================================================

In GRPO:

    advantages = inputs["advantages"]    # shape: (B,)   — one scalar per completion
    advantages = advantages.unsqueeze(1) # shape: (B, 1) — ready to broadcast

When multiplied by per_token_loss (shape B, T):
    coef_1 * advantages  →  (B,T) * (B,1) = (B,T)

All tokens in the same completion see the SAME advantage:

    Completion A (advantage = +2.0):
      Token: t=0    t=1    t=2    t=3
      Adv:  [+2.0, +2.0,  +2.0, +2.0]   <-- broadcast from scalar

    Completion B (advantage = -1.0):
      Token: t=0    t=1    t=2    t=3
      Adv:  [-1.0, -1.0, -1.0, -1.0]   <-- broadcast from scalar

The ratio coef_1 is STILL per-token (different at each position):
    Completion A ratios: [1.1, 0.9, 1.3, 1.0]   <-- per-token

So per_token_loss for Completion A:
    = -min(1.1*2.0, clip(1.1)*2.0), -min(0.9*2.0, clip(0.9)*2.0), ...
    Each token has a DIFFERENT loss value, but they are all scaled by the SAME +2.0

WHY:
    GRPO has no value network → no temporal credit assignment → cannot say which
    token was better within a completion. All we know is the WHOLE completion was
    good or bad relative to its sibling completions.

SECTION 9 — IMPORTANCE SAMPLING: TOKEN VS SEQUENCE LEVEL
================================================================

Source: grpo_trainer.py lines 2496-2506

CODE:
------
    log_ratio = per_token_logps - old_per_token_logps   # shape: (B, T)

    if self.importance_sampling_level == "token":
        log_importance_weights = log_ratio              # shape: (B, T) — per token

    elif self.importance_sampling_level == "sequence":
        log_importance_weights = (log_ratio * mask).sum(-1) \
                               / mask.sum(-1).clamp(min=1.0)    # shape: (B,)
        log_importance_weights = log_importance_weights.unsqueeze(-1)  # shape: (B,1)

    coef_1 = torch.exp(log_importance_weights)

WHAT THIS COMPUTES:
-------------------
    Token level:    coef_1[b,t] = pi_theta(token_t) / pi_old(token_t)
                    Each token gets its OWN importance weight.

    Sequence level: coef_1[b] = exp( (1/T) * sum_t[ log(pi_theta(t)/pi_old(t)) ] )
                              = (pi_theta(sequence) / pi_old(sequence)) ^ (1/T)
                              = geometric mean of per-token ratios
                    All tokens in a sequence share the SAME importance weight.

CONCRETE EXAMPLE:
-----------------
Batch=2, max length=4 tokens.

mask (1=real, 0=padding):
    Seq A: [1, 1, 1, 0]   <- 3 real tokens, 1 padding
    Seq B: [1, 1, 0, 0]   <- 2 real tokens, 2 padding

log_ratio = per_token_logps - old_per_token_logps:
    Seq A: [+0.1, -0.1, -0.2, 0.0]
    Seq B: [+0.1, -0.1,  0.0, 0.0]

--- Token level ---
    coef_1 = exp(log_ratio):
    Seq A: [exp(0.1), exp(-0.1), exp(-0.2), exp(0.0)]
         = [1.105,    0.905,     0.819,     1.0  ]    <- different per token

--- Sequence level ---
    Step 1: zero out padding
        log_ratio * mask:
        Seq A: [0.1,  -0.1, -0.2, 0.0]
        Seq B: [0.1,  -0.1,  0.0, 0.0]

    Step 2: sum over tokens
        Seq A: 0.1 + (-0.1) + (-0.2) = -0.2
        Seq B: 0.1 + (-0.1)          =  0.0

    Step 3: divide by real token count
        mask.sum(-1) = [3, 2]
        log_importance_weights = [-0.2/3,  0.0/2] = [-0.067, 0.000]

    Step 4: unsqueeze to (B,1)
        log_importance_weights = [[-0.067], [0.000]]

    coef_1 = exp(log_importance_weights):
           = [[0.935], [1.000]]   <- one scalar per sequence, broadcast to all tokens

WHY SEQUENCE LEVEL:
-------------------
    advantages are (B,) — one per sequence.
    Using sequence-level IS weights matches that granularity.
    Also avoids numerical explosion from multiplying many per-token ratios
    (the product would be pi_theta(seq)/pi_old(seq) which can blow up for long sequences).

MATH:
    sequence-level coef_1 = exp(mean_t[log r_t])
                          = (product_t[r_t]) ^ (1/T)
                          = geometric mean of token ratios

SECTION 10 — masked_whiten AND masked_fill IN PPO
================================================================

Source: ppo_trainer.py lines 524-525

CODE:
------
    advantages = masked_whiten(advantages, ~padding_mask)
    advantages = torch.masked_fill(advantages, padding_mask, 0)


PROBLEM WITHOUT THESE OPERATIONS:
----------------------------------
In a batch, sequences have different lengths. Padding tokens are added.
After GAE, padding positions contain values that are numerically small (near 0)
but are meaningless. If we naively compute mean/std over all positions including
padding, the statistics get corrupted.

CONCRETE EXAMPLE:
-----------------
Batch of 2 sequences, max response length = 5:

    Seq A (real length=3): real tokens at t=0,1,2 — padding at t=3,4
    Seq B (real length=4): real tokens at t=0,1,2,3 — padding at t=4

    padding_mask:
        Seq A: [F, F, F, T, T]
        Seq B: [F, F, F, F, T]
    (True = padding)

    advantages after GAE:
        Seq A: [1.37, 0.65, 0.50, 0.0, 0.0]   (padding has near-zero values)
        Seq B: [0.80, 0.40, 0.20, 0.10, 0.0]


--- Step 1: masked_whiten(advantages, ~padding_mask) ---

    WITHOUT masking (wrong — includes padding zeros):
        all values: [1.37, 0.65, 0.50, 0.0, 0.0, 0.80, 0.40, 0.20, 0.10, 0.0]
        mean = 0.402,  std = 0.43

        normalized Seq A: [2.25, 0.58, 0.23, -0.94, -0.94]
                                                ^^^^^^^^^^^^
                                Padding zeros normalized to -0.94!
                                (Zero is below the mean, so after normalization
                                 it becomes a large negative number.)

    WITH masking (correct — only real tokens contribute to stats):
        valid values: [1.37, 0.65, 0.50, 0.80, 0.40, 0.20, 0.10]
        mean = 0.574,  std = 0.41

        whitened Seq A: [1.99, 0.19, -0.18, -1.40, -1.40]
                                              ^^^^^^^^^^^^^
                                After whitening, padding positions now have
                                garbage value -1.40 (they were included in
                                the arithmetic x - mean / std)


--- Step 2: masked_fill(advantages, padding_mask, 0) ---

    Zero out the garbage values at padding positions:

        Before: [[1.99,  0.19, -0.18, -1.40, -1.40],
                 [0.55, -0.42, -0.91, -1.16, -1.40]]

        After:  [[1.99,  0.19, -0.18,  0.0,   0.0 ],  <- padding zeroed out
                 [0.55, -0.42, -0.91, -1.16,  0.0 ]]  <- padding zeroed out


WHY BOTH STEPS ARE NEEDED TOGETHER:
-------------------------------------
    Step 1 alone: valid tokens are correctly normalized, but padding positions
                  contain large garbage values (-1.40) after whitening.

    Step 2 alone (without step 1): advantages are at their raw unwhitened scale.
                  Training is unstable because gradient magnitudes vary wildly
                  across batches.

    Both together:
        - Valid tokens: properly normalized (zero-mean, unit-variance across batch)
        - Padding tokens: exactly 0 → contribute 0 to policy gradient

WHY PADDING MUST BE ZERO IN THE LOSS:
--------------------------------------
    In the training loop:
        pg_losses = -mb_advantage * ratio

    If padding advantage were -1.40 instead of 0:
        pg_loss at padding = -(-1.40) * ratio = +1.4 * ratio  <- FAKE gradient!
        This would spuriously push the model to assign higher probability to
        padding tokens, which are meaningless tokens that should be ignored.

    With advantage = 0:
        pg_loss at padding = -(0) * ratio = 0  <- no gradient from padding

SECTION 11 — REWARD MODEL OUTPUT: PPO vs GRPO
================================================================

COMMON MISCONCEPTION:
"In PPO, the reward model gives per-token rewards. In GRPO, it gives per-sequence."

REALITY:
Both PPO and GRPO reward models return ONE SCALAR PER SEQUENCE.

PPO code:
    _, score, _ = get_reward(reward_model, postprocessed_query_response, ...)
    # score shape: (batch,)  <- one scalar per sequence

GRPO code:
    rewards = (rewards_per_func * self.reward_weights).nansum(dim=1)
    # shape: (batch,)  <- one scalar per sequence

So why does PPO have per-token structure and GRPO does not?

    PPO: rewards array starts as per-token KL penalties, scalar reward added
         at last token. Value network (critic) then decomposes this into
         per-token advantages via GAE.

    GRPO: no KL in reward signal, no value network. Scalar reward is used
          directly → normalized to produce ONE advantage per sequence.

DIAGRAM:
--------
    PPO reward signal:
    Token: t=0    t=1    t=2    t=3 (last real)   t=4 (pad)
           -0.02  -0.01  -0.03  -0.01 + 2.5 (score)   0
           ^KL^   ^KL^   ^KL^   ^KL^ + ^reward_model^

    GRPO reward signal:
    One number for the whole sequence: R = 1.0
    (No per-token structure until value network creates it — and GRPO has none)

================================================================

ANSWER: It comes from the VALUE NETWORK (critic), not the reward model.

    PPO with critic:
        1. Reward model -> scalar R
        2. KL penalty   -> per-token r_kl[t]
        3. Combined reward per token:  rewards[t] = r_kl[t] (+ R at last token)
        4. Critic predicts V(s_t) at every position
        5. GAE uses rewards[t] + gamma*V(s_{t+1}) - V(s_t) at each t
        6. Result: advantages[b, t]  shape (batch, T) — DIFFERENT per token

    GRPO without critic:
        1. Reward model -> scalar R
        2. KL penalty added to LOSS, not reward signal
        3. No value network → no temporal decomposition possible
        4. Normalize R within group: A = (R - mean) / std
        5. Result: advantages[b]  shape (batch,) — ONE per completion

SECTION 13 — DPO: DIRECT PREFERENCE OPTIMIZATION
================================================================

Reference: TRL grpo_trainer.py dpo_trainer.py

WHAT IS DPO?
------------
DPO trains a language model directly from preference pairs (chosen, rejected)
WITHOUT a separate reward model and WITHOUT an RL training loop.

Data format:
    (prompt x,  chosen response y_w,  rejected response y_l)
    Human says: y_w is better than y_l for this prompt.

DERIVATION:
-----------
Step 1: The RLHF objective is:
    max_pi  E[r(x,y)] - beta * KL[pi(y|x) || pi_ref(y|x)]

Step 2: The optimal policy under this objective is:
    pi*(y|x) = (1/Z(x)) * pi_ref(y|x) * exp(r(x,y) / beta)

    Where Z(x) = sum_y pi_ref(y|x) * exp(r(x,y)/beta)  (partition function)

Step 3: Rearrange to express reward in terms of policy:
    r(x,y) = beta * log(pi*(y|x) / pi_ref(y|x)) + beta * log Z(x)

Step 4: Apply Bradley-Terry preference model:
    P(y_w preferred over y_l | x) = sigma(r(x, y_w) - r(x, y_l))

Step 5: Substitute the reward expression (log Z(x) cancels!):
    P(y_w > y_l | x) = sigma(
        beta * log(pi(y_w|x)/pi_ref(y_w|x))
        - beta * log(pi(y_l|x)/pi_ref(y_l|x))
    )

Step 6: DPO loss = negative log-likelihood of Step 5:

    L_DPO = -E[ log sigma( beta * (log pi_theta(y_w|x) - log pi_ref(y_w|x))
                          - beta * (log pi_theta(y_l|x) - log pi_ref(y_l|x)) ) ]

SHORTHAND:
----------
    chosen_logratio   = log pi_theta(y_w|x) - log pi_ref(y_w|x)
    rejected_logratio = log pi_theta(y_l|x) - log pi_ref(y_l|x)
    delta_score       = chosen_logratio - rejected_logratio

    L_DPO = -log sigma(beta * delta_score)

    Positive delta_score → chosen is more likely relative to ref than rejected → low loss
    Negative delta_score → rejected improved more than chosen → high loss (needs correction)


CODE (TRL dpo_trainer.py):
--------------------------
    # Both chosen and rejected run through current model AND reference model
    chosen_logps,     rejected_logps     = logps.chunk(2, dim=0)
    ref_chosen_logps, ref_rejected_logps = ref_logps.chunk(2, dim=0)

    # Log ratios: how much current model differs from reference
    chosen_logratios   = chosen_logps   - ref_chosen_logps    # log(pi_theta/pi_ref) for chosen
    rejected_logratios = rejected_logps - ref_rejected_logps  # log(pi_theta/pi_ref) for rejected

    # Delta score
    delta_score = chosen_logratios - rejected_logratios

    # DPO loss (sigmoid type — the standard DPO)
    per_sequence_loss = -F.logsigmoid(self.beta * delta_score)
    loss = per_sequence_loss.mean()

NOTE ON LOG PROBS:
    In practice, logps are SUMMED (or averaged) over the completion tokens:
    log pi(y|x) = sum_t [ log pi(token_t | x, token_0..token_{t-1}) ]
    This gives one scalar per completion.


CONCRETE NUMERICAL EXAMPLE:
----------------------------
    beta = 0.1
    Prompt: "What is the capital of France?"
    Chosen:   "Paris"
    Rejected: "I don't know"

    log pi_theta(chosen)   = -1.2  (current model probability of "Paris")
    log pi_ref(chosen)     = -1.5  (reference model probability of "Paris")

    log pi_theta(rejected) = -0.8  (current model probability of "I don't know")
    log pi_ref(rejected)   = -0.9  (reference model probability of "I don't know")

    chosen_logratio   = -1.2 - (-1.5) = +0.3  (model improved chosen vs ref)
    rejected_logratio = -0.8 - (-0.9) = +0.1  (model also slightly improved rejected)

    delta_score = 0.3 - 0.1 = +0.2  (chosen improved MORE than rejected)

    loss = -log sigma(0.1 * 0.2)
         = -log sigma(0.02)
         = -log(0.505)
         = 0.683

    Good case (model correctly prefers chosen):
    After more training steps, say:
        chosen_logratio   = +0.8
        rejected_logratio = -0.3
        delta_score = 0.8 - (-0.3) = 1.1

        loss = -log sigma(0.1 * 1.1) = -log sigma(0.11) = -log(0.527) = 0.641  (lower)

    Bad case (model strongly prefers rejected):
        chosen_logratio   = -0.1
        rejected_logratio = +0.8
        delta_score = -0.1 - 0.8 = -0.9  (NEGATIVE — wrong direction!)

        loss = -log sigma(0.1 * (-0.9)) = -log sigma(-0.09) = -log(0.478) = 0.738  (higher)


GRADIENT INTUITION:
-------------------
    d/d_theta L_DPO = -beta * (1 - sigma(beta * delta_score))
                      * grad(chosen_logratio - rejected_logratio)

    = -beta * (1 - sigma(...)) * [grad log pi_theta(y_w|x) - grad log pi_theta(y_l|x)]

    Effect:
    (a) INCREASES log probability of chosen y_w
    (b) DECREASES log probability of rejected y_l
    (c) Scaled by (1 - sigma(...)): if model already strongly prefers chosen, gradient
        is small (already learned). If model is wrong, gradient is large.

ROLE OF REFERENCE MODEL:
-------------------------
    Without pi_ref:
        Just maximizing log pi_theta(y_w) and minimizing log pi_theta(y_l).
        Model can drift far from base behavior (e.g., degenerate outputs).

    With pi_ref:
        chosen_logratio = log pi_theta(y_w) - log pi_ref(y_w)
        Measures improvement RELATIVE to reference.
        Model is incentivized to stay close to pi_ref on unchosen directions.
        This is the KL constraint made implicit.

DPO LOSS VARIANTS (also in TRL):
---------------------------------
    sigmoid  (standard DPO):   -log sigma(beta * delta_score)
    hinge:                      relu(1 - beta * delta_score)
    ipo:                        (delta_score/T - 1/(2*beta))^2  (length normalized)
    robust:                     smoothed version for noisy labels

### 1.1 Proximal Policy Optimization (PPO) Source Code Mapping

The core operational logic for executing PPO training steps, computing temporal sequence advantages, and calculating loss gradients is located within the production file:
👉 `huggingface/trl/blob/main/trl/trainer/ppo_trainer.py`

Within this file, the concrete execution sequence for optimization happens inside the main training step loop. Instead of manually applying programmatic gradients via custom derivative calculations, the system constructs a combined optimization loss scalar. When the trainer invokes the distributed acceleration backend, PyTorch’s auto-differentiation engine automatically populates the weight gradients across the disparate model layers.

#### 1. Calculate Advantage (Generalized Advantage Estimation)

The PPO implementation tracks trajectories by looping backward through generated sequence steps. This allows future rewards to travel upstream to early token selections, striking a fine balance between bias and variance:

```python
# Exact conceptual execution framework inside trl/trainer/ppo_trainer.py
lastgaelam = 0
advantages_list = []

# Loop backward from the terminal token of the response length
for t in reversed(range(response_length)):
    nextvalues = values[:, t + 1] if t < response_length - 1 else next_values
    
    # Calculate the immediate 1-step Temporal Difference residual
    delta = rewards[:, t] + self.config.gamma * nextvalues - values[:, t]
    
    # Accumulate future discounted residuals using GAE factors
    lastgaelam = delta + self.config.gamma * self.config.lam * lastgaelam
    advantages_list.append(lastgaelam)

# Reverse back to normal chronological sequence ordering
advantages = torch.stack(advantages_list[::-1], dim=1)

# White-noise normalize the advantages across the mini-batch to stabilize policy gradients
advantages = (advantages - advantages.mean()) / (advantages.std() + 1e-8)

```

#### 2. Calculate Gradients for Actor Model (Policy)

The Actor network is updated by finding the probability ratio between the active policy weights and the historical reference rollout policy weights. This ratio is subsequently constrained via a clipping threshold to prevent severe training degradation:

```python
# Extract the exponential difference to find the token probability ratio
ratio = torch.exp(logprobs - old_logprobs)

# Compute the twin surrogate clipped loss functions
pg_losses = -advantages * ratio
pg_losses2 = -advantages * torch.clamp(
    ratio, 
    1.0 - self.config.cliprange, 
    1.0 + self.config.cliprange
)

# Take the maximum negative objective (minimizing the upper bound of the loss)
policy_loss = torch.max(pg_losses, pg_losses2).mean()

```

#### 3. Calculate Gradients for Critic Model (Value Function)

The Critic head network tracks historical reward structures to minimize the Mean Squared Error (MSE) between its local state estimations and the empirical GAE returns. To prevent the Critic from altering its weights too drastically in a single optimization step, TRL clips the value function output:

```python
# Clip the value predictions relative to historical baseline estimates
vpred_clipped = old_values + torch.clamp(
    vpred - old_values,
    -self.config.cliprange_value,
    self.config.cliprange_value,
)

# Compute the mean squared errors for raw vs clipped predictions
vf_losses1 = (vpred - returns) ** 2
vf_losses2 = (vpred_clipped - returns) ** 2

# Select the conservative maximum error penalty bound
vf_loss = 0.5 * torch.max(vf_losses1, vf_losses2).mean()

```

#### 4. The Joint Backward Pass

To optimize compute performance when the Actor and Critic share identical underlying transformer backbone layers, TRL combines both independent loss values into a single tracking scalar. Calling `.backward()` on this scalar populates the gradients for both networks simultaneously:

```python
# Aggregate policy optimization and value function error terms
loss = policy_loss + self.config.vf_coef * vf_loss

# Distributed accelerator backend computes gradients for both Actor and Critic blocks
self.accelerator.backward(loss)

```

### 1.2 Group Relative Policy Optimization (GRPO) Source Code Mapping

To resolve the massive GPU memory overhead induced by hosting a dedicated Critic network, modern reasoning workflows leverage Group Relative Policy Optimization. The source implementation is located within:
👉 `huggingface/trl/blob/main/trl/trainer/grpo_trainer.py`

Because GRPO drops the Value function completely, it eliminates the backward-in-time sequence loops and value clipping blocks. Instead, all mathematical steps are condensed into a vectorized execution method named `_compute_loss`.

#### 1. Calculate Advantage (Group Relative Normalization)

Instead of relying on a Critic's baseline prediction, GRPO samples a parallel group of independent answers ($G$) for every unique input prompt. It computes advantages by running a Z-score calculation directly across the scores of that group:

```python
# Conceptual matrix implementation inside trl/trainer/grpo_trainer.py
# rewards shape: [batch_size, num_generations_per_prompt]

# Compute group-wide descriptive statistics
mean_rewards = rewards.mean(dim=1, keepdim=True)
std_rewards = rewards.std(dim=1, keepdim=True)

# Advantage calculation maps group performance into relative variances
# Better-than-average choices receive positive gains; below-average choices receive negative cuts
advantages = (rewards - mean_rewards) / (std_rewards + 1e-4)

```

#### 2. Calculate Gradients for Actor Model

Because there is no Critic, the calculated group advantage is directly broadcasted down to the token resolution matrix. The system applies a per-token policy gradient calculation, utilizing an explicit validation mask to bypass padding blocks:

```python
# Extract log-probability ratios at token-level accuracy
logratio = per_token_logps - old_per_token_logps
ratio = torch.exp(logratio)

# Apply standard PPO-style surrogate clipping boundaries
surrogate1 = ratio * advantages
surrogate2 = torch.clamp(
    ratio, 
    1.0 - self.config.cliprange, 
    1.0 + self.config.cliprange
) * advantages

# Compute standard policy loss component
per_token_loss = -torch.min(surrogate1, surrogate2)

```

#### 3. Calculate Gradients for Critic Model

* **GRPO Architecture Implementation Rule:** This step does not exist. The Critic network is completely deleted from the computing infrastructure. The line execution count and weight matrix initialization size for a Critic head are exactly zero.

#### 4. The Unified Loss Formulation with KL Regularization

To prevent the language policy from distorting its vocab vocabulary choices into nonsensical syntax while optimizing for pure reward extraction, GRPO incorporates an explicit Kullback-Leibler (KL) divergence penalty directly against a frozen reference base model:

```python
# Integrate policy loss along with a hard anchor to the original model distribution
loss = per_token_loss + self.config.beta * kl_divergence

# Mask out irrelevant padding segments and isolate true generated tokens
loss = (loss * completion_mask).sum() / completion_mask.sum()

# Standard gradient extraction pass
self.accelerator.backward(loss)

```

## SECTION 2: ARCHITECTURAL PRINCIPLES DEEP DIVE

To build systems using these tools, we must map out the mathematical foundation that dictates their runtime execution behaviors.

### 2.1 The Generalized Advantage Estimation (GAE) Framework

The core challenge in Reinforcement Learning is **Credit Assignment**—determining exactly which specific token or action caused a long-term outcome. GAE solves this by using an exponential tuning slider, denoted as **Lambda ($\lambda$)**, to bridge the two traditional evaluation methods:

* **Monte Carlo (High Variance, Zero Bias):** The algorithm waits for an entire sentence or episode to conclude, collects the final score, and applies that evaluation to every token in the chain. This approach introduces high variance because thousands of valid paths can lead to the same terminal score, introducing severe noise into the gradient.
* **1-Step Temporal Difference (Low Variance, High Bias):** The algorithm looks exactly one step ahead. It takes an action, samples the immediate reward, and loops in its Critic's future prediction to guess the rest of the path value. This introduces high bias because if the Critic's predictive weights are imperfect, the Actor optimizes its weights based on flawed assumptions.

#### GAE Mathematical Equation

GAE combines these two approaches by computing an exponentially weighted moving average of all future Temporal Difference residuals:

```
Advantage = Delta_t + (Gamma * Lambda) * Delta_t+1 + (Gamma * Lambda)^2 * Delta_t+2 + ...

```

Where the individual single-step prediction error is defined as:

```
Delta_t = Reward_t+1 + (Gamma * Next_State_Value) - Current_State_Value

```

#### The Autonomous Car Credit Assignment Sequence

Imagine an autonomous car navigating a track. At Second 2, it makes an unstable steering choice.

```
[Sec 1: Stable] ──► [Sec 2: BAD TURN] ──► [Sec 3: Wobbling] ──► ... ──► [Sec 60: CRASH]

```

* **If Lambda = 0 (Pure 1-Step Lookahead):** The algorithm only evaluates Second 3. At Second 3, the car hasn't crashed yet and is still safely on the track, so the immediate reward is recorded as positive (+1). The system fails to realize the steering choice at Second 2 was dangerous because it cut off its future evaluation horizon too early.
* **If Lambda = 1 (Pure Monte Carlo Path):** The system waits until the vehicle crashes at Second 60. It applies a massive penalty (-100) and propagates it uniformly across all 60 seconds. This pollutes the gradient because perfectly safe straight-line driving choices made at Seconds 10, 20, and 45 are blamed for a crash caused much earlier.
* **If Lambda = 0.95 (GAE Balance):** The algorithm tracks the cascading drop in value predictions at Seconds 3, 4, and 5. This localized shock wave travels backward through the exponential decay formula, applying a strong, targeted penalty to the bad steering choice at Second 2. Meanwhile, distant, unrelated events at Second 50 are naturally dampened out by the exponential decay factor.

### 2.2 The Bellman Formula and Universal Error Design

The mathematical blueprint of reinforcement learning relies heavily on the **Bellman Equation**, which breaks the valuation of a long-term strategy into a recursive function:

```
Current Value Estimation = Immediate Reward + Discounted Future Value Estimation

```

When implemented in a neural network, this equation functions as a structural error check. If the model's predictions are perfectly accurate, both sides of the equation balance out cleanly. However, when the model's predictions diverge from empirical rollouts, the resulting variance is defined as the **Temporal Difference (TD) Error**:

```
TD Error = (Immediate Reward + Discounted Next Value Prediction) - Current Value Prediction

```

This underlying architecture explains the striking visual similarity between the Q-Learning function update and the Actor-Critic TD Error equation:

```
Q-Learning Parentheses Segment:
( Reward + Gamma * Max_Action Q(S_t+1, a) ) - Q(S_t, A_t)

Actor-Critic TD Error (Delta_t) Segment:
( Reward + Gamma * V(S_t+1) ) - V(S_t)

```

Both equations calculate the direct mathematical variance between an empirical reality step and an active future prediction model. The structural differences between them stem entirely from their assumptions regarding future strategy execution.

---

### 2.3 On-Policy vs. Off-Policy Training Constraints

Understanding how algorithms process data requires defining the relationship between the active data-collection policy and the target optimization model:

* **On-Policy (The Active Participant):** The model can only learn from data collected by its own active weight configuration. If the network parameters shift even slightly, the historical training logs are rendered invalid and must be discarded.
* **Off-Policy (The Detached Analyst):** The model can optimize its strategy by analyzing data generated by an external source, such as a different user, an old version of the model, or historical log buffers.

```
On-Policy Exploration Path (Expected Value Tracking):
                 ┌─── Action 1 (Prob: 70%) ──► Evaluate Path 1
State S_t ───────┼─── Action 2 (Prob: 20%) ──► Evaluate Path 2
                 └─── Action 3 (Prob: 10%) ──► Evaluate Path 3
                 [Calculates the total weighted expected average of current ability]

Off-Policy Exploration Path (Max Value Tracking):
                 ├─── Action 1 (Value: 10)
State S_t ───────┼─── Action 2 (Value: 100) ──► SELECT THIS MAX TARGET NODE ALWAYS
                 └─── Action 3 (Value: 45)
                 [Completely ignores active exploration probability tracking]

```

#### Why Q-Learning Uses Maximum Selection (Off-Policy)

Q-Learning calculates targets using a maximum operator over all possible future actions: `Max_a Q(S_t+1, a)`. This mathematical design assumes **absolute execution perfection in the future**.

It does not care if the active agent is currently configured to make highly random choices 50% of the time for exploration purposes; its target calculation evaluates the state assuming the agent will always select the absolute best mathematical move from that step forward.

#### Why Actor-Critic and PPO Use Expected Value Baselines (On-Policy)

The Critic model tracks states using an expected value formulation: `V(S_t+1)`. This approach scales predictions based on the **active, imperfect abilities of the current Actor model**. If the Actor model is currently unstable and has a high statistical probability of making a catastrophic mistake in the next step, that baseline incompetence is natively baked directly into the Critic's estimation.

#### The Necessity of On-Policy Alignment for Large Language Models

When optimizing Large Language Models via RLHF alignment, the training system must remain strictly **On-Policy** (such as PPO or GRPO).

If you attempt to train an LLM using an off-policy replay buffer filled with text generated several hours prior, the model will waste massive compute optimizing for token combinations that matched its historical parameters. However, language networks change drastically with minor weight updates. A sentence structure generated five hours ago might now have a near-zero probability of ever being sampled again by the active model.

By utilizing On-Policy tracking, the gradient updates ensure that the model is constantly evaluating and correcting its active linguistic distribution.

| **Baseline Target Source** | Dynamic parametric model tracking step-by-step state estimations ($V(s)$). | Pure statistical mean ($\text{Mean}(r)$) calculated across parallel output instances. |
| **Compute Operation Profile** | Sequential backward looping sequences tracking step residuals. | Vectorized, highly parallelized forward matrix transformations across batch groups. |
| **Optimization Constraints** | Probability bounding via surrogate policy clipping thresholds. | Combined objective optimization using token-clipping wrapped with an explicit KL penalty. |

## SECTION 4: DIAGNOSTIC HANDBOOK — COMMON PRODUCTION FAILURES AND BUG FIXES

Implementing GRPO in large-scale reasoning and mathematical training systems introduces unique edge cases and failure modes. This section outlines common production failures, their root causes, and clear resolution guidelines.

### Failure Case 1: Trajectory Stalling and Zero-Loss Gradients

#### The Production Symptom

During early training phases on a complex reasoning dataset, the training metrics show that the Actor model's loss values drop to absolute zero. The model stops optimizing, text output alignment degrades, and the system fails to learn even basic formatting rules.

#### The Mathematical Root Cause

This issue often stems from a strict, deterministic reward structure (such as an exact-match regular expression checking for explicit XML format tags like `<reasoning>` and `<answer>`) paired with an insufficient initial sampling group size ($G$).

If the base model is untrained, it will fail to output the exact required string schemas across all parallel instances in a group. As a result, every single response option ($O_1$ through $O_G$) receives an identical reward score of `0.0`. When this happens, the descriptive statistics for that group collapse:

```
Rewards Vector = [0.0, 0.0, 0.0, 0.0]
Group Mean = 0.0
Group Standard Deviation = 0.0

```

When the standard deviation reaches absolute zero, the advantage normalization formula divides by zero (or clips against a tiny epsilon value), outputting an identical advantage score of `0.0` for every token. This nullifies the surrogate policy gradients, completely stalling training updates.

#### The Production Bug Fix

To resolve this, you must modify your reward evaluation pipeline to ensure non-zero variance during early training iterations. Implement a soft fallback structure that awards partial credit for incremental progress, such as generating valid brackets, maintaining appropriate sequence lengths, or outputting clean numeric characters:

```python
# Unstable Production Implementation
def calculate_rewards_unstable(completion_strings):
    rewards = []
    for text in completion_strings:
        # Rigid regex matching causes group variance to collapse to zero early on
        if re.search(r"<think>.*?</think>\s*<answer>.*?</answer>", text, re.DOTALL):
            rewards.append(1.0)
        else:
            rewards.append(0.0)
    return torch.tensor(rewards)

# Stabilized Production Bug Fix
def calculate_rewards_stabilized(completion_strings):
    rewards = []
    for text in completion_strings:
        score = 0.0
        
        # Soft validation checks guarantee incremental reward signals
        if "<think>" in text: score += 0.2
        if "</think>" in text: score += 0.2
        if "<answer>" in text: score += 0.2
        if "</answer>" in text: score += 0.2
        
        # Strict structural validation reward Component
        if re.search(r"<think>.*?</think>\s*<answer>.*?</answer>", text, re.DOTALL):
            score += 1.0
            
        rewards.append(score)
        
    rewards_tensor = torch.tensor(rewards)
    
    # Defensive programming: force a tiny baseline variance if standard deviation collapses
    if rewards_tensor.std() == 0:
        # Inject microscopic fractional noise to break symmetric mathematical deadlocks
        rewards_tensor += torch.randn_like(rewards_tensor) * 1e-6
        
    return rewards_tensor

```

### Failure Case 2: Verbosity Explosion and Sequence Length Bias

#### The Production Symptom

The model discovers a shortcut to game the reward matrix. It begins generating excessively long sentences filled with repetitive reasoning steps and redundant phrase loops, eventually exceeding memory allocations and throwing Out-Of-Memory (OOM) errors.

#### The Mathematical Root Cause

This issue occurs when token-level loss tracking is calculated as a raw, non-normalized sum across completion tokens.

Longer sequences accumulate a higher cumulative loss value simply by containing more tokens, bias gradients toward long, verbose outputs. The model learns that it can artificially inflate its advantage scores by extending its generations, using verbosity to shield itself from optimization penalties.

#### The Production Bug Fix

To stabilize training, you must normalize the loss metrics using an explicit completion mask. This ensures that the final gradient steps are scaled strictly by the number of valid tokens generated, removing any mathematical incentives for unnecessary verbosity:

```python
# Unstable Production Implementation
# Calculates raw sums, which biases gradients toward longer sequences
raw_loss = per_token_loss + beta * kl_divergence
unstable_loss = (raw_loss * completion_mask).sum() 

# Stabilized Production Bug Fix
# Normalizes updates against sequence lengths to ensure unbiased gradients
raw_loss = per_token_loss + beta * kl_divergence
stabilized_loss = (raw_loss * completion_mask).sum() / completion_mask.sum()

```

**GRPO vs PPO Comprehensive Manual**  
**Group Relative Policy Optimization (GRPO) in Hugging Face TRL**

---

### 1. Introduction

This manual compares **PPO** (Proximal Policy Optimization) and **GRPO** (Group Relative Policy Optimization) as implemented in the Hugging Face `trl` library.

**PPO** is the classic RLHF method.  
**GRPO** is a newer, simpler, and more stable variant (inspired by DeepSeekMath) designed especially for reasoning and verifiable reward tasks.

---

### 2. Core Philosophy Difference

**PPO**:  
Uses a **Value Function** + **GAE** to estimate advantage. Requires a critic (value head).

**GRPO**:  
Uses **Group-Relative Advantage** — no value function needed. For each prompt, generate multiple completions (a "group"), then compute advantage **relative to the group**.

This makes GRPO much simpler and more stable for tasks with verifiable rewards (math, code, format, accuracy).

---

### 3. Advantage Calculation

#### PPO Advantage (Classic)

```python
# Simplified from old ppo_trainer.py around line 517
advantages = returns - value_preds
advantages = (advantages - advantages.mean()) / (advantages.std() + 1e-8)
```

Or with GAE:
- delta = reward + gamma * next_value - value
- advantages = delta + gamma * lambda * next_advantage

#### GRPO Advantage (Group Relative)

```python
# From grpo_trainer.py
rewards = torch.tensor(rewards)  # shape: [batch_size * num_generations]

# Reshape to groups
rewards_grouped = rewards.view(-1, self.num_generations)

mean_group = rewards_grouped.mean(dim=1)
std_group  = rewards_grouped.std(dim=1)

mean_group = mean_group.repeat_interleave(self.num_generations)
std_group  = std_group.repeat_interleave(self.num_generations)

advantages = rewards - mean_group

if self.scale_rewards != "none":
    advantages = advantages / (std_group + 1e-4)
```

**Key Insight**: Advantage is computed **within each prompt's generation group**.

---

### 4. Full Loss Computation in GRPO

GRPO mainly uses a **fused Liger kernel** for efficiency.

#### Main Loss Terms:

1. **Clipped Policy Gradient** (core learning signal)
2. **KL Divergence Penalty** (controlled by `beta`)
3. **Importance Sampling Correction** (for vLLM generation)

**Simplified GRPO Loss Structure**:

```python
loss = clipped_surrogate_loss + beta * kl_loss
```

Where the clipped surrogate is:

```python
ratio = exp(current_logps - old_logps)
clipped_ratio = torch.clamp(ratio, 1 - epsilon_low, 1 + epsilon_high)

policy_loss = -torch.min(
    ratio * advantages,
    clipped_ratio * advantages
)
```

**Full fused call** (from current `grpo_trainer.py`):

```python
loss = liger_grpo_loss(
    _input=hidden_states,
    lin_weight=lm_head_weight,
    selected_token_ids=completion_token_ids,
    attention_mask=loss_mask,
    advantages=advantages,
    old_per_token_logps=old_logps,
    ref_per_token_logps=ref_logps,      # for KL
    beta=beta,                          # KL coefficient
    epsilon_low=0.2,
    epsilon_high=0.2,
    # ... other params
)
```

---

### 5. Structural ASCII Diagrams

#### GRPO Training Flow

```
Prompt
   ↓
Generate N completions (Group)  ← vLLM or HF generate
   ↓
Compute Reward for each completion (e.g. accuracy, format, code exec)
   ↓
Group-Relative Advantage = reward - group_mean
   ↓
Compute logprobs (current policy + old policy + reference policy)
   ↓
Liger Fused Loss (Clipped PG + KL + Importance Sampling)
   ↓
Update Policy
```

#### Comparison: PPO vs GRPO

```
PPO:
Prompt → Generate → Reward → Value Function → GAE Advantage → Clipped PG + KL

GRPO:
Prompt → Generate Group (N samples) → Reward → Group-Relative Advantage → Clipped PG + KL
```

---

### 6. Key Hyperparameters in GRPO

- `num_generations`: 4~16 (how many completions per prompt)
- `beta`: KL penalty coefficient (0.01 ~ 0.1 typical)
- `scale_rewards`: "group", "batch", or "none"
- `epsilon_low` / `epsilon_high`: Clipping range
- `use_liger_kernel`: Highly recommended (much faster)

### 7. Diagnostic Troubleshooting Guide

**Common Errors & Fixes**

| Error / Symptom                        | Root Cause                                      | Fix |
|---------------------------------------|--------------------------------------------------|-----|
| `NaN loss`                            | Advantages have extreme values                   | Use `scale_rewards="group"` + small epsilon |
| Very unstable training                | `num_generations` too small                      | Increase to 8~16 |
| Model collapses / ignores prompt      | KL beta too low                                  | Increase `beta` to 0.05~0.1 |
| Slow training                         | Not using Liger kernel                           | Set `use_liger_kernel=True` |
| Reward not improving                  | Group size too small or reward function noisy    | Improve reward function + increase group size |
| Out of memory                         | Large `num_generations` + long sequences         | Reduce `num_generations` or use vLLM |
| Importance sampling warning           | Using vLLM without correction                    | Enable importance sampling in GRPO config |

**Use PPO when**:
- You need dense reward signals
- You have a good value function

SECTION 17 —  is GAE one type of q learning algorithm? 
================================================================



No, **GAE (Generalized Advantage Estimation)** is not a type of Q-learning algorithm. They belong to two completely different families of reinforcement learning methods.

The easiest way to understand the difference is: **Q-learning is an algorithm used to decide what action to take**, while **GAE is a mathematical tool used to evaluate how good an action was after the fact.**

Here is the breakdown of how they differ in purpose, family, and mathematical architecture.

---

## 1. The Core Differences

| Feature              | Q-Learning                                        | GAE (Generalized Advantage Estimation) |
| ---                  | ---                                               | ---                           |
| **Family**           | **Value-Based Method**                            | **Policy Gradient Method** (Actor-Critic) |
| **Primary Output**   | Action-Values ($Q(s,a)$)                          | Advantages ($A^{\text{GAE}}$) |
| **Core Question**    | "What is the best action to take right now?"      | "How much better was this action compared to my average expectation?" |
| **How it's used**    | Direct action selection via $\max_{a} Q(s,a)$.    | Used as a baseline filter to calculate stable gradients for an **Actor** network. |

---

## 2. Where GAE Fits in the RL Taxonomy

To see why they don't overlap, we have to look at the two main branches of Modern Reinforcement Learning:

```
                  Reinforcement Learning
                            │
         ┌──────────────────┴──────────────────┐
         ▼                                     ▼
   Value-Based                           Policy Gradient (Actor-Critic)
(Learns Q-values directly)             (Learns the strategy directly via steps)
         │                                     │
  ┌──────┴──────┐                       ┌──────┴──────┐
  ▼             ▼                       ▼             ▼
Q-Learning     DQN                     PPO           TRPO
                                        │
                                        ▼
                               Uses GAE to calculate
                               stable advantage scores

```

### A. The Q-Learning Family (Value-Based)

In Q-learning, you do not have a neural network that represents a "strategy" or "policy." Instead, you train a network to map out the future value of every single possible action ($Q(s, a)$). To act, the agent simply scans the choices and picks the one with the highest mathematical score ($\max_{a} Q(s, a)$).

### B. The PPO/TRPO Family (Policy Gradient + GAE)

In advanced algorithms like PPO (used heavily in LLM alignment/RLHF), the agent has an **Actor network** that directly outputs probabilities for actions.

To train the Actor smoothly, you need to know the **Advantage ($A$)** of an action. The Advantage is defined as:

A(s, a) = Action Value  Q(s, a) - Baseline State Value  V(s)

* If $A > 0$, the action was better than average (tell the Actor to do it more).
* If $A < 0$, the action was worse than average (tell the Actor to avoid it).

**GAE is specifically the algorithm designed to calculate this Advantage ($A$) value as accurately and stably as possible.** ---

## 3. Why we don't use Q-learning calculations in GAE

GAE relies completely on calculating **State Values ($V(s)$)** using the Bellman Equation to check prediction errors step-by-step:

delta_t = R_{t+1} + \gamma V(S_{t+1}) - V(S_t)

It aggregates these $V(s)$ errors across time steps to construct the advantage score. It completely bypasses the maximum-action calculation ($\max_{a} Q(s,a)$) that defines the core mechanics of Q-learning.

## Summary

GAE is not a version of Q-learning. Instead, think of **Q-learning** as an all-in-one standalone engine for simple or discrete environments (like video games), while **GAE** is a specialized high-performance component tucked inside modern **Actor-Critic networks** (like PPO) to optimize complex, continuous control behaviors and large language models.
